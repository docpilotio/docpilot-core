# RFC-0049: v0.5 Release Provenance and Determinism Gate

## Status

Implemented and locally verified. Final Release Evidence collection is pending an
exact clean integration commit.

## 1. Purpose

RFC-0048 completed the durable Core Review Bundle workflow and exposed it through
the official CLI. DocPilot can now analyze, generate, review, resume, and safely
apply documentation changes, but its release evidence remains distributed across
console output, test XML, smoke artifacts, handoffs, and Git inspection.

RFC-0049 defines one deterministic, machine-verifiable release evidence contract
for the v0.5 milestone. A release candidate is acceptable only when the manifest
is bound to the exact source revision, required compatibility contracts, test
aggregate, smoke artifacts, and scope checks that were actually verified.

This RFC establishes release trust. It does not publish a release.

## 2. Product outcome

A maintainer or automation process can:

1. collect evidence for one exact release candidate;
2. persist a canonical Release Evidence Manifest;
3. verify the manifest later without rerunning successful checks;
4. reject missing, corrupt, stale, contradictory, or policy-incomplete evidence;
5. produce deterministic JSON and Markdown gate reports;
6. make a manual release decision from one auditable record.

## 3. Scope

RFC-0049 includes:

- Release Evidence Manifest format version 1;
- exact Core commit identity and repository state evidence;
- embedded MCP mode and identity evidence;
- public compatibility contract versions;
- build and test execution evidence;
- deterministic test XML aggregation;
- official CLI review workflow smoke evidence;
- stable CLI exit-code and JSON-output contract checks;
- artifact size and SHA-256 evidence;
- protected-scope and documentation synchronization checks;
- deterministic JSON encoding and Markdown gate reporting;
- strict manifest decoding and integrity verification;
- stale source and stale artifact detection;
- versioned v0.5 gate policy;
- offline verification after dependencies and evidence are available.

## 4. Non-goals

RFC-0049 does not:

- push, merge, tag, sign, publish, or create a GitHub Release;
- choose or migrate a CI vendor;
- change Core runtime generation, review, or apply semantics;
- change DIR, snapshot, Review Bundle, or CLI JSON formats;
- add Review Bundle retention, archival, migration, or Apply Receipt;
- require live OpenAI or Ollama calls by default;
- certify provider output quality;
- add MCP product features or make Core depend on MCP;
- update MCP project state automatically;
- create a general-purpose workflow engine;
- store credentials, environment values, or full process logs;
- promise byte-reproducible JAR archives unless separately proven.

Review Bundle Lifecycle and Apply Receipt remain a later RFC candidate.

## 6. Architecture

Release verification is repository tooling outside the Core runtime:

```text
Gradle task or release verifier
        -> evidence collectors
        -> release evidence domain and policy evaluator
        -> canonical codec
        -> JSON manifest + Markdown gate report
```

Dependency direction:

```text
release tooling -> public Core/CLI contracts
Core runtime    -X-> release tooling
Core runtime    -X-> MCP
```

Process execution, Git inspection, filesystem traversal, and JUnit XML loading are
adapters. Policy and canonical encoding must be testable without processes, Git,
Gradle, or MCP.

## 7. Operations

Two operations are distinct:

```text
collect
verify
```

- `collect` runs approved checks and atomically writes new evidence.
- `verify` strictly loads existing evidence, revalidates local artifacts and
  candidate identity, then evaluates policy without rerunning build or test.
- Neither operation mutates Git, MCP state, source, tests, or planning.
- Verification performs no network access.

Candidate Gradle integration:

```text
gradlew.bat releaseEvidenceCollect --release-id v0.5.0-rc.1
gradlew.bat releaseEvidenceVerify --manifest <path>
```

Exact task names may follow implementation conventions.

## 8. Release Evidence Manifest format 1

Top-level fields use this fixed order:

```text
releaseEvidenceFormatVersion
releaseId
candidate
contracts
executions
testAggregate
artifacts
compatibilityChecks
scopeChecks
policy
gate
integrity
```

Unknown, missing, duplicated, or type-invalid fields are rejected. Version 1
decoding does not silently default evidence.

`releaseId` is explicit and matches:

```text
v<major>.<minor>.<patch>-rc.<positive-integer>
```

RFC-0049 does not create or require a Git tag with that name.

## 9. Candidate identity

Candidate fields:

```text
coreCommit
branch
repositoryClean
mcpMode
mcpCommit
mcpVersion
```

Rules:

- `coreCommit` is an exact 40-character lowercase Git object ID;
- commit identity, not branch name, is authoritative;
- collection requires clean tracked files, untracked files, and index;
- merge, rebase, cherry-pick, and bisect states are rejected;
- `HEAD` must equal the requested candidate before and after collection;
- repository state must remain unchanged throughout collection;
- v1 supports `EMBEDDED` MCP;
- embedded `mcpCommit` equals `coreCommit`;
- MCP version is read from the canonical package metadata and validated;
- a future separate MCP repository requires a revised contract.

## 10. Public contract evidence

Required contract fields:

```text
dirSchemaVersion
specificationSnapshotFormatVersion
reviewBundleFormatVersion
cliOutputFormatVersion
cliExitCodeContractVersion
```

The v0.5 expected values at specification time are:

```text
DIR schema: 0.3
Specification Snapshot: 1
Review Bundle: 1
CLI JSON output: 1
CLI exit-code contract: 1
```

Collectors read authoritative code contracts. They do not accept unchecked
command-line values for these fields.

## 11. Execution evidence

Each execution record contains:

```text
id
kind
commandArguments[]
workingDirectory
exitCode
result
required
outputArtifactIds[]
```

Rules:

- records are sorted by `id`;
- commands are argument vectors, never shell text;
- paths are repository-relative with `/`;
- environment variables, durations, timestamps, and full logs are excluded;
- missing required executions and non-zero exits fail;
- cached, `UP-TO-DATE`, or `NO-SOURCE` test outcomes cannot satisfy clean tests.

Minimum required executions:

```text
core-clean-build
core-clean-test
cli-review-smoke
cli-exit-code-contract
cli-json-contract
diff-check
protected-scope-check
documentation-sync-check
```

## 12. Build and test policy

Required commands:

```text
gradlew.bat clean build
gradlew.bat clean test
```

JUnit XML aggregation:

- discovers only approved Gradle test-result directories;
- parses every discovered testsuite;
- sums XML files, tests, failures, errors, and skipped;
- rejects malformed XML, duplicate canonical paths, and contradictory counts;
- requires tests greater than zero;
- requires failures `0`, errors `0`, and skipped `0`;
- requires result files produced by the current clean test execution;
- rejects cached, up-to-date, no-source, or stale evidence.

Exact test count is evidence, not a hard-coded threshold. When a comparison
manifest is explicitly supplied, a count decrease fails unless a separately
approved exception identifier is present. This RFC does not define an exception
approval system.

## 13. CLI smoke

An isolated fixture must cover fresh processes for:

```text
review prepare
review inspect
review status (pending)
review decide
review status (ready)
review apply
```

The smoke verifies:

- expected exit codes;
- JSON output format 1;
- proposal ID, normalized Bundle Path, and Payload SHA-256;
- pending `3`, success `0`, stale/conflict `4`, and invalid bundle `5`;
- deterministic repeated inspect/status output;
- applied documentation is non-empty;
- applied bytes match the reported SHA-256;
- original `architecture-samples` is unchanged.

An approved deterministic fixture provider is mandatory. Live provider smoke is
optional and does not affect the default gate.

## 14. Artifact evidence

Each artifact contains:

```text
id
kind
path
sizeBytes
sha256
required
producerExecutionId
```

Rules:

- paths are repository-relative or fixture-relative and use `/`;
- absolute host paths and traversal are rejected;
- SHA-256 is lowercase hexadecimal;
- required files are regular, readable, and non-empty unless explicitly allowed;
- duplicate IDs and paths are rejected;
- artifacts are sorted by `id`;
- producer execution must exist and pass;
- verification re-hashes locally available required artifacts;
- missing or changed required artifacts fail.

Required kinds:

```text
JUNIT_XML_SET
CLI_JSON_RESULT
REVIEW_BUNDLE
APPLIED_DOCUMENTATION
DIFF_CHECK_RESULT
SCOPE_CHECK_RESULT
DOCUMENTATION_SYNC_RESULT
```

Build archives may be optional. RFC-0049 does not claim reproducible archives
until independent clean builds prove identical bytes.

## 15. Compatibility checks

Required checks:

```text
DIR_SCHEMA_0_3
SPECIFICATION_SNAPSHOT_FORMAT_1
REVIEW_BUNDLE_FORMAT_1
CLI_JSON_OUTPUT_FORMAT_1
CLI_EXIT_CODE_CONTRACT_1

RFC_0048_THIN_CLI_ADAPTER
MCP_EMBEDDED_IDENTITY
CORE_HAS_NO_MCP_RUNTIME_DEPENDENCY
```

Each check records stable ID, expected value, actual value, result, and referenced
artifact IDs. Unknown/missing required IDs, dangling references, or contradictory
PASS results are rejected.

## 16. Scope and documentation checks

Scope evidence records:

- candidate and optional comparison commit;
- changed tracked paths in lexical order;
- forbidden generated paths;
- repository cleanliness;
- submodule state when applicable.

The gate rejects tracked runtime logs, `.kotlin/errors`, unapproved build output,
and protected-path changes without an approved scope declaration.

Required documentation:

```text
Canonical RFC
Main Planning
Completion Handoff
Roadmap
Release Evidence Manifest
Release Gate Report
```

Synchronization is evaluated by structured RFC identity and status rules, not
filenames alone. The gate cannot pass while Canonical documents describe
RFC-0049 as unimplemented.

## 17. v0.5 policy

Policy identity:

```text
DOCPILOT_V0_5
```

Mandatory rules:

- exact clean candidate commit;
- embedded MCP identity;
- clean build and clean test PASS;
- zero failures, errors, and skipped tests;
- required CLI smoke and stable contracts PASS;
- all required artifacts present and intact;
- all compatibility checks PASS;
- scope and documentation checks PASS;
- manifest integrity PASS.

Optional stricter checks are permitted. Mandatory rules cannot be disabled while
retaining the `DOCPILOT_V0_5` identity.

## 18. Gate evaluation

Evaluation is total, binary, and fail-closed:

```text
valid and every mandatory rule passes -> PASS
anything else                         -> FAIL
```

There is no `PASS_WITH_WARNINGS`.

Stable failure codes:

```text
UNSUPPORTED_FORMAT
INVALID_MANIFEST
INTEGRITY_MISMATCH
CANDIDATE_MISMATCH
DIRTY_REPOSITORY
MCP_IDENTITY_MISMATCH
MISSING_EXECUTION
EXECUTION_FAILED
CACHED_TEST_EVIDENCE
INVALID_TEST_AGGREGATE
TEST_FAILURES
TEST_ERRORS
TESTS_SKIPPED
MISSING_ARTIFACT
ARTIFACT_MISMATCH
COMPATIBILITY_FAILED
SCOPE_FAILED
DOCUMENTATION_NOT_SYNCHRONIZED
REPOSITORY_CHANGED_DURING_COLLECTION
```

Multiple failures follow this order, then evidence ID.

## 19. Canonical JSON and integrity

Canonical JSON is:

- UTF-8;
- LF line endings;
- two-space indentation;
- one trailing newline;
- fixed field order;
- arrays sorted by documented stable keys;
- lowercase SHA-256;
- free of timestamps, durations, absolute paths, usernames, and hostnames.

Equivalent semantic evidence produces byte-identical JSON.

Integrity:

```json
{
  "algorithm": "SHA-256",
  "payloadSha256": "<64 lowercase hex>"
}
```

The payload is the canonical encoding of all top-level fields except `integrity`.
Strict decoding reconstructs and hashes the payload, then rejects the complete
manifest on mismatch. This checksum proves integrity and identity, not author
authentication or signature.

## 20. Markdown gate report

The Markdown report is a deterministic projection of a validated manifest, never
a second source of truth.

Required sections:

```text
Release Candidate
Source Identity
Public Contracts
Build and Tests
CLI Verification
Artifacts
Compatibility
Scope
Documentation
Gate Decision
Failure Reasons
Manifest SHA-256
```

It contains no current time or machine path and can be regenerated
byte-identically from the same manifest.

## 21. Output, atomicity, and concurrency

Default generated output:

```text
build/release-evidence/<release-id>/
  release-evidence.json
  release-gate.md
  artifacts/
```

- generated output is not committed by default;
- Completion Handoff records the final manifest SHA and durable location;
- explicit locations cannot target repository root, `.git`, source directories,
  or another candidate directory;
- collection writes to a unique temporary sibling directory;
- publication occurs only after all content is validated;
- existing candidate evidence is never overwritten;
- concurrent collection for one release ID yields one winner and one conflict;
- cleanup targets only temporary paths created by that invocation;
- failed verification never mutates evidence.

## 22. Exit-code contract

If a command entry point is implemented:

| Code | Symbol | Meaning |
| ---: | --- | --- |
| 0 | `RELEASE_GATE_PASSED` | Valid manifest and passing policy |
| 2 | `USAGE_ERROR` | Invalid invocation |
| 3 | `RELEASE_GATE_FAILED` | Valid evaluation with gate failures |
| 4 | `STALE_EVIDENCE` | Candidate or artifact no longer matches |
| 5 | `INVALID_EVIDENCE` | Malformed, unsupported, or corrupt evidence |
| 6 | `EXECUTION_FAILED` | Required collection command failed |
| 7 | `EVIDENCE_IO_FAILED` | Safe evidence I/O failed |
| 70 | `INTERNAL_ERROR` | Unexpected failure |

These do not change RFC-0048 review CLI exit codes.

## 23. Security and privacy

Canonical evidence must not contain:

- environment variables or provider keys;
- credential-bearing remote URLs;
- full user home paths;
- arbitrary stdout/stderr;
- non-fixture Review Bundle comments.

Diagnostics are sanitized. Commands and paths use symbolic arguments and
repository-relative values.

## 24. Determinism boundary

RFC-0049 guarantees deterministic evidence modeling, encoding, aggregation,
evaluation, and report rendering for equivalent inputs.

It does not guarantee identical:

- process durations or console logs;
- live provider output;
- archive bytes before archive reproducibility is proven;
- absolute host paths.

Non-deterministic diagnostics cannot affect manifest identity or gate result.

## 27. Verification plan

### 27.1 Model, codec, and integrity

- valid round trip and byte-identical encoding;
- fixed field and collection order;
- unknown, missing, duplicate, and invalid fields rejected;
- path and line-ending normalization before modeling;
- checksum mismatch rejects the whole manifest.

### 27.2 Candidate identity

- exact clean commit passes;
- dirty tracked, untracked, or staged state fails;
- merge/rebase/cherry-pick state fails;
- HEAD movement during collection fails;
- embedded MCP mismatch and invalid version fail.

### 27.3 Build and tests

- clean build/test pass;
- non-zero execution and zero tests fail;
- failures/errors/skipped fail;
- malformed or duplicate XML fails;
- stale/cached/up-to-date results fail;
- comparison-manifest count regression fails.

### 27.4 CLI smoke

- prepare-to-apply across separate processes;
- pending/ready/stale/invalid exit codes;
- JSON version and identity fields;
- deterministic inspect/status;
- exact applied-document checksum;
- isolated fixture and unchanged source samples.

### 27.5 Artifacts, scope, and policy

- missing, empty, changed, duplicate, and dangling artifacts;
- traversal and absolute paths rejected;
- repository mutation during collection;
- protected generated-file detection;
- atomic publication conflict;
- every mandatory failure code and deterministic ordering;
- no pass-with-warning route;
- mandatory-rule disabling rejected.

### 27.6 Regression

- RFC-0046 REMOVE tests;
- RFC-0047 persistence/integrity/resume tests;
- RFC-0048 review CLI tests;
- full clean build and test;
- isolated architecture-samples validation;
- `git diff --check`;
- protected-path review;
- offline verification.

## 28. Completion criteria

RFC-0049 is complete only when:

1. Manifest format 1 is implemented and documented;
2. equivalent evidence produces byte-identical JSON;
3. integrity failure rejects the complete manifest;
4. exact clean commit and embedded MCP identity are enforced;
5. cached test output cannot satisfy clean-test evidence;
6. JUnit totals are deterministic and strict;
7. v0.5 requires zero failures, errors, and skipped tests;
8. official review CLI smoke is captured and verified;
9. artifact integrity and producer links are enforced;
10. compatibility, scope, and documentation checks are complete;
11. stale evidence fails closed;
12. gate evaluation returns only PASS or FAIL;
13. JSON and Markdown are deterministic;
14. existing evidence can be verified offline;
15. collection is atomic and never overwrites evidence;
16. Core runtime has no dependency on release tooling or MCP;
17. targeted, integration, regression, and isolated smoke tests pass;
18. RFC, Planning, Handoff, and Roadmap match the evidence;
19. no push, tag, publication, or release occurs automatically.

## 29. Risks

- Gradle cached-task detection requires structured task outcomes.
- JUnit XML can be double-counted by naive nested-suite parsing.
- Git state can change during collection.
- Host-specific paths can leak into canonical evidence.
- SHA-256 integrity is not reviewer authenticity.
- Over-broad collection can leak environment or provider data.
- Incorrect module placement can reverse the dependency direction.

Each risk requires a fail-closed test.

## 30. Deferred follow-up

Not approved by RFC-0049:

- Review Bundle lifecycle, retention, archival, and migration;
- durable Apply Receipt;
- authenticated reviewer identity;
- manifest signing or transparency logs;
- SBOM/SLSA or external provenance services;
- reproducible archive certification;
- remote artifact storage or CI-specific adapters;
- automatic tag, release, publication, or MCP orchestration.

Review Bundle Lifecycle and Apply Receipt is the recommended RFC-0050 candidate,
subject to separate approval.
